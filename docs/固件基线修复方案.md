# kebab mainline pmOS 固件基线修复方案 2026-06-01

## 根因（3 路研究一致确认，high confidence）

错误链：spmi pmic_arb transaction failed → pmic-spmi probe failed (-EIO) → smps2 could not find RPMh address。

本质：**不是内核/DTB bug，是 vendor firmware 基线不匹配**。
- SM8250 的 PMIC regulator 不能由 AP 直接写，要经 RPMh 协处理器。
- mainline qcom-rpmh-regulator 通过 cmd_db_read_addr() 把 regulator 名(smps2)解析成 RPMh 硬件地址。
- cmd-db 表是 **aop (Always-On Processor) firmware 在 boot 时填充的**，存在 SMEM 保留内存区。
- 当前设备固件是 **OxygenOS 15 / Android 15**，aop/cmd-db/xbl/tz 太新，mainline 解析不出 RPMh 地址 → regulator 全挂 → 卡早期 boot。
- pmOS **不会**刷 aop/cmd-db/xbl，它只覆盖 super/boot/dtbo，所以沿用了设备上 OOS15 的固件 → 失败。

## 修复方向

把 vendor firmware 降到 **OxygenOS Android 13 或 14 基线**（kebab mainline/LineageOS 验证过的基线），再重启已刷好的 pmOS。
- 权威参考：LineageOS kebab fw_update 页要求 "Android 13/14 full stock ROM"。
- pmOS 的 boot/super/dtbo 已经刷好且没问题，**只需补刷 vendor firmware 分区**。

## 需要刷的固件分区（从 OOS13/14 payload.bin 提取，--slot=all 刷双槽）

通用：abl aop bluetooth cmnlib64 cmnlib devcfg dsp featenabler hyp imagefv keymaster logo mdm_oem_stanvbk modem multiimgoem qupfw spunvm storsec tz uefisecapp
XBL（按 DDR 类型，刷错直接硬砖）：
- DDR4/type0：xbl.img + xbl_config.img
- DDR5/type1：xbl_lp5.img + xbl_config_lp5.img
关键：aop + xbl + xbl_config + devcfg + tz 是修复 RPMh 的核心。

## 致命风险（务必先确认）

1. **DDR 类型刷错 XBL = 永久硬砖**。必须先 `adb shell getprop ro.boot.ddr_type`（0=LPDDR4X, 1=LPDDR5）。但现在设备进不了 Android（卡 pmOS），需从别的途径确认（8T KB2000 多为 LPDDR5/type1，但不能猜）。
2. **Anti-Rollback (ARB) e-fuse**：从 OOS15 降到 Android13/14 可能被 ARB 拒绝甚至砖。需确认要降到的 build 的 ARB index <= 设备已熔断值。OOS15 → 13/14 跨度大，ARB 是真实风险。
3. **型号必须精确匹配** KB2000/KB2003 CN，用错 region 固件会 "device not match" 或砖。
4. spunvm / mdm_oem_stanvbk 无 a/b 槽。
5. MSM/EDL 兜底是 Windows-only、非官方、只修 slot A。

## 获取固件

- Oxygen Updater app / oxygenupdater.com 下 full(非增量) OOS13/14 ROM。
- 镜像源：github.com/spike0en/oneplus_archive。
- payload-dumper-go (github.com/ssut/payload-dumper-go) 提取 payload.bin → 各分区 .img。
- 注意 OnePlus OTA 服务器 2024-09 起拦截浏览器 UA，用 aria2 或 app 下。

## 关键决策点（需用户拍板）

- ARB 风险：从 OOS15 降到 Android13/14 不是零风险，最坏 ARB 不匹配可能砖（需 EDL 救，且只救 slot A）。
- DDR 类型：刷 XBL 前必须 100% 确认，否则硬砖。设备当前进不了系统，要想办法读 ddr_type。
- 备选更安全方案：放弃 mainline，用 **downstream 内核**（pmbootstrap kernel=downstream），downstream 用厂商 4.19 内核，不依赖 mainline RPMh 路径，可能直接在 OOS15 固件上跑起来，不用动 vendor firmware（零硬砖风险）。功能不如 mainline 但稳。

## 2026-06-01 二次核验修订（high confidence，源码+pmaports 实证）

### 根因再确认（比第一版更精确）
- 报错确切出处：`drivers/regulator/qcom-rpmh-regulator.c` L482-487：`vreg->addr = cmd_db_read_addr(name); if (!vreg->addr){ dev_err("could not find RPMh address for resource %s"); return -ENODEV; }`。
- 关键：这是 **-ENODEV** 路径，不是 **-EPROBE_DEFER**。`drivers/soc/qcom/cmd-db.c`：cmd-db 内存没映射时 `cmd_db_ready()` 先返回 -EPROBE_DEFER（不同报错）；只有 cmd-db **已经被读到、但表里查不到 `smps2` 这个资源名** 才会走 -ENODEV "could not find"。
- 因此结论收紧：**DTS/DTB 没错**。mainline `arch/arm64/boot/dts/qcom/sm8250.dtsi` 里 `cmd_db: memory@80860000 { compatible="qcom,cmd-db"; reg=<0x0 0x80860000 0x0 0x20000>; no-map; }` 是固定物理地址、正确的。驱动确实读到了那块 SMEM，只是 **设备上 OOS15 的 aop 固件填充的 cmd-db 表内容/资源命名，mainline 解析不出 `smps2` 的地址**。本质仍是 **vendor firmware（aop/cmd-db）基线不匹配**，不是内核或 DTB bug。

### downstream 不是逃生门（修正第一版乐观判断）
- pmaports MR !3993（OnePlus 8 Pro instantnoodlep）原文：downstream kernel "patched primary for debugging purposes... **It only boots to telnet / initramfs shell at this point.**"
- 即 SM8250 OnePlus 8 系的 pmOS **downstream 4.19 内核根本进不了可用 rootfs，只到 initramfs 调试 shell**。所以"用 downstream 绕过 RPMh 直接把系统跑起来"在 pmOS 里目前不成立。downstream 仅供调试。
- kebab 当前 `device/testing/device-oneplus-kebab/APKBUILD` 仍是旧式单内核：`depends="linux-oneplus-kebab"`（= LineageOS android_kernel_oneplus_sm8250 的 4.19.110 fork，commit 0c1bed1...）。
- 对比：instantnoodlep 已迁到双内核拆分 `subpackages="$pkgname-kernel-downstream / -kernel-mainline"`，mainline 子包 depends `linux-postmarketos-qcom-sm8250` 标 "(recommended)"，downstream 标 "(not recommended, for debugging purposes)"。pmbootstrap init 选内核就是选这个子包。
- 2025-05 pmOS 博客 + pkgs.postmarketos.org 显示 kebab 也加了 mainline（!6411）；但 master device 包文件可能滞后，实际以 `pmbootstrap init` 时是否给出 kernel 选择 + `apk info -R device-oneplus-kebab` 为准。

### stable 通道（v25.12）能否解
- 换 stable 通道只改 userland 版本与内核**快照点**，不改变"mainline 依赖 vendor aop/cmd-db 提供 RPMh 地址"这一架构事实。若卡 smps2，stable 一样卡，除非该 stable 锁定的内核版本恰好带了能容忍当前固件的 regulator 改动——概率低，不作为修复主路径。

### 修复优先级（修订）
1. 首选仍是把 vendor firmware 降到 kebab mainline 验证过的 **Android 13/14 OOS 基线**（LineageOS fw_update 要求），重点刷 aop+xbl(+config 按 DDR)+devcfg+tz；这是让 cmd-db 暴露 mainline 能解析的 `smps2` 等 RPMh 资源的根因修复。先 `getprop ro.boot.ddr_type` 定 DDR，再防 ARB。
2. downstream 不能当"跑起来"的退路，只能 initramfs 调试。
3. stable 通道不是解药。
